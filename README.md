# ga4-realtime

A live terminal dashboard for GA4's Realtime report — one property, or several
at once.

GA4's Realtime report only reaches back 30 minutes and the standard reports lag
4–8 hours behind, so traffic that happens while nobody is watching the screen is
lost. This tool polls that window on a schedule, accumulates it into SQLite, and
draws a "today so far" view from the accumulated history.

One process, two jobs: a polling thread per site writes, and the main thread
renders from the same database. The dashboard shows one site at a time and `Tab`
moves between them.

**Close the terminal and collection stops.** The dashboard is the only
collector: nothing here runs in the background, as a service, or on a timer. A
headless collector was considered and deliberately left out of this version, so
what you get is what you watched — see
[What it does not do](#what-it-does-not-do).

You need Python 3.11 or newer, a GA4 property, and permission to create a
service account in the Google Cloud project behind it.

---

## Install

With [pipx](https://pipx.pypa.io/), which keeps the tool and its dependencies
out of every other environment you have:

```bash
pipx install git+https://github.com/fchamone/ga4_realtime
```

Or with `pip`, into whatever environment you want it in:

```bash
pip install git+https://github.com/fchamone/ga4_realtime
```

The package is not on PyPI yet. Once it is, both commands lose their URL and
become `pipx install ga4-realtime` / `pip install ga4-realtime`; nothing else
about them changes.

From a clone — which is what you want if you intend to read or change the code:

```bash
git clone https://github.com/fchamone/ga4_realtime
cd ga4_realtime
python3 -m venv .venv                                   # macOS, Linux
.venv/bin/python -m pip install -e .
```

```powershell
git clone https://github.com/fchamone/ga4_realtime
cd ga4_realtime
py -m venv .venv                                        # Windows
.venv\Scripts\python.exe -m pip install -e .
```

Either way you end up with one command, `ga4-realtime`, generated by the
packaging metadata and identical on Linux, macOS and Windows. It works from any
working directory and needs no virtualenv activation; `python -m ga4_realtime …`
is equivalent to `ga4-realtime …` everywhere, if you would rather be explicit
about which interpreter is running. Check the install with:

```bash
ga4-realtime --version
```

Two notes on the dependencies. Python 3.11 is the floor because the config
format is TOML and `tomllib` entered the standard library there. And `tzdata` is
a hard requirement rather than a convenience: Windows ships no IANA timezone
database at all, and every day boundary in this tool is computed in the
property's own timezone.

`constraints.txt` is a full `pip freeze` of the author's exact working set, and
it is entirely opt-in:

```bash
pip install -e . -c constraints.txt
```

Reach for it only when an upstream release has broken something and you want a
set known to work while you find out what. Continuous integration deliberately
does *not* apply it, so an upstream break shows up as a red build rather than
being discovered months later.

## Five minutes to a dashboard

```bash
ga4-realtime init      # 1. write a starter config here
                       # 2. fill in two fields
ga4-realtime doctor    # 3. check them, without polling anything
ga4-realtime           # 4. the dashboard
```

**1.** `ga4-realtime init` writes `ga4-realtime.toml` and `.env.example` into
the current directory. It refuses to overwrite either, naming the file it would
have destroyed. `--path` puts the config somewhere else — for instance
`ga4-realtime init --path ~/.config/ga4-realtime/config.toml`, which is where
every working directory can find it.

**2.** Two fields in that file cannot be guessed and are left for you:

```toml
[defaults]
credentials = "secrets/ga4-service-account.json"   # where you saved the key

[[sites]]
name        = "mysite"
property_id = ""                                   # the NUMERIC id
```

`property_id` is empty and `credentials` points at a path where nothing is saved
yet, so the config refuses to load until you have sorted out both — with a
message naming what to fix, rather than a permission error from the API an hour
later. The next section is where those two values come from.

While you are in the file, look at `conversions`. The starter config guesses
`["purchase", "sign_up"]`; it should name the events your property actually
reports, spelled exactly as GA4 spells them. There is no default that could be
right, and an empty list would show a conversion count of zero forever without
ever saying that nothing was configured.

**3.** `ga4-realtime doctor` reports, per site: config valid, credentials
readable, Data API reachable, Admin API reachable or the UTC fallback, timezone
resolvable — and, once the config loads, the resolved database and log paths.
Run straight after `init`, with the two fields still empty, it stops at the
config line and names every gap it found instead. It writes nothing: it never
opens the database or the log, so neither is created by running it. It exits 1
when it finds a problem, so it is also usable from a script.

**4.** `ga4-realtime` opens the dashboard. `q` quits.

## GA4 access (once)

The tool reads the GA4 APIs with a service account. Five steps, all outside this
repository:

1. [Google Cloud Console](https://console.cloud.google.com/) → create or pick a
   project → **APIs & Services** → enable the **Google Analytics Data API** and
   the **Google Analytics Admin API** as well. They are two distinct APIs: the
   second is the one that returns the property's display name and timezone, and
   without it `ga4-realtime` warns and falls back to UTC day boundaries.
2. **IAM & Admin → Service accounts** → create a service account. It needs no
   role at all on the project: the permission that matters is step 4.
3. On the account just created → **Keys → Add key → Create new key → JSON**.
   Save the file wherever your config's `credentials` key points — by default
   `secrets/ga4-service-account.json`, relative to the config file itself.
4. GA4 → **Admin → Property access management** → add the service account's
   e-mail (`something@project.iam.gserviceaccount.com`) with the **Viewer**
   role. Without this the API answers `PermissionDenied` even with the right
   credential.
5. GA4 → **Admin → Property settings** → copy the **Property ID** (numeric) into
   `property_id` in your config file.

Step 5 is where almost everyone trips: the property ID is a number. The
`G-XXXXXXXXXX` in the site's HTML is the *measurement ID*, which is for
`gtag.js` and is no use to the API — it produces a `PermissionDenied` that never
mentions the real cause. That is why the config rejects a `G-` value by name,
before any call is made.

One service account can serve every site you configure, or each site can name
its own key. Sites sharing a key share one API client rather than opening one
each.

## Using it

```bash
ga4-realtime                                   # the live dashboard
ga4-realtime --site clientb                    # open focused on one site
ga4-realtime --interval 60 --window 12         # poll faster, wider chart
ga4-realtime --ascii --verbose

ga4-realtime report                            # today, every site
ga4-realtime --site clientb report --date 2026-08-05
ga4-realtime sites                             # what is configured and stored
ga4-realtime doctor
ga4-realtime init --path ~/.config/ga4-realtime/config.toml

ga4-realtime --db /path/to/copy.db report      # a database from elsewhere
ga4-realtime --db /path/to/copy.db sites
```

`--site`, `--db` and the rest are *global* flags: they mean the same thing on
every command, including the bare dashboard, and either side of the subcommand
word is fine. `ga4-realtime --site clientb report` and
`ga4-realtime report --site clientb` are the same line. Type one on both sides
and the last one wins.

| Command | What it does |
|---|---|
| *(none)* | the live dashboard — poll, accumulate, render, until you quit |
| `report` | the daily summary as plain text, from the local database alone |
| `sites` | every site in all three of its states: enabled, disabled, orphaned — or simply stored, when `--db` names a database and no config says which |
| `init` | write a starter config and `.env.example`; never overwrites |
| `doctor` | check config and API access per site; polls nothing, writes nothing |

**Only the dashboard and `doctor` reach the API.** `report` and `sites` read the
local SQLite: each site's property name and timezone come from what the live
view cached there, so both work with `--db` alone — no config file, no
credentials, no network. That is what makes a database copied off another
machine readable: `ga4-realtime --db /path/to/copy.db report`.

**Piping or redirecting stdout skips the live view.** `ga4-realtime | cat` still
authenticates and does one priming poll of every site, then prints exactly what
`ga4-realtime report` prints and exits — a script parsing one parses the other.
It is the cheapest end-to-end check that everything is wired up.

### Global flags

One spelling works on `ga4-realtime` itself and on every subcommand, and on
either side of the subcommand word: `ga4-realtime --db copy.db report` and
`ga4-realtime report --db copy.db` are the same line. The dashboard has no
subcommand word at all, which is why these are global rather than per-command
in the first place.

| Flag | Effect |
|---|---|
| `--config PATH` | the config file to read; otherwise the search below |
| `--site NAME` | which site to act on; `all` means every site |
| `--db PATH` | the SQLite file, relative to the current directory |
| `--interval SECONDS` | seconds between polls |
| `--refresh SECONDS` | seconds between redraws |
| `--window HOURS` | hours of history on the chart's x axis, 1 to 24 |
| `--timezone ZONE` | force every site's day boundaries into one zone |
| `--ascii` | plain ASCII plots and bars |
| `--verbose` | add a log panel to the dashboard, and log at debug level |
| `--version` | print the version and exit |

`report` adds `--date YYYY-MM-DD`, and `init` adds `--path`.

### `--site`, per command

`--site` is a global flag like the rest, so either
`ga4-realtime --site clientb report` or `ga4-realtime report --site clientb`
says the same thing.

| | `--site NAME` | `--site all` | omitted |
|---|---|---|---|
| dashboard | opens focused on NAME | same as omitted | opens on the first enabled site |
| `report` | that site only | every site, then a combined total when there is more than one | same as `all` |
| piped stdout | that site's summary | every site's summary | every site's summary |
| `sites`, `doctor`, `init` | accepted and ignored — each of them always covers everything it knows about | | |

The dashboard is the one command where the name has to be a site the *config*
knows and has enabled; `report` and `sites` accept any site the database has
ever recorded, orphans included.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | something you can fix — printed without a traceback, naming the file to edit and the fix. `doctor` also exits 1 when it finds a problem |
| 2 | the arguments were wrong (argparse's own convention) |
| 130 | interrupted with Ctrl-C |

### Keys in the live view

| Key | Action |
|---|---|
| `q`, `Ctrl-C` | quit — every polling thread is joined first |
| `Tab`, `n` | next site |
| `p` | previous site |
| `1`–`9` | jump to site N, in the order the config file lists the enabled sites |
| `r` | redraw now, without waiting out the refresh interval |

Data is written on every poll, so quitting never loses what was already
collected. `Shift-Tab` is deliberately not bound: on Windows it arrives as a
two-character extended sequence, which the key reader swallows by design, and
teaching it to assemble sequences is the first step of reimplementing curses.

### What is on screen

An identity line (which site, which timezone, the clock, how long ago the last
poll succeeded), a status strip carrying one marker per site, the cumulative
chart, today's events by count, and a footer of totals.

| Marker | ASCII | Meaning |
|---|---|---|
| `●` | `*` | last poll succeeded, within two intervals |
| `✗` | `!` | last poll failed |
| `○` | `.` | not polled yet, or stale beyond two intervals |

The strip is what stops a site nobody has pressed `Tab` to from failing quietly,
which is the one real weakness of showing a single site at a time. The
`--verbose` log panel is site-prefixed and interleaves every site's lines for
the same reason.

## Configuration

One TOML file. `ga4-realtime init` writes a starter version, and
`ga4-realtime.example.toml` in this repository documents every key with the
reasoning behind it.

### Where the file is looked for

Three places, in order, and no more:

1. `--config PATH`, if given. An explicit path is an answer rather than a first
   guess: the file exists or the run fails, because falling through to the
   others after a typo would silently load a *different* config than the one
   asked for.
2. `./ga4-realtime.toml`, in the current working directory.
3. The platform config directory:
   - Linux/BSD: `$XDG_CONFIG_HOME/ga4-realtime/config.toml`, default
     `~/.config/ga4-realtime/config.toml`
   - macOS: `~/Library/Application Support/ga4-realtime/config.toml`
   - Windows: `%APPDATA%\ga4-realtime\config.toml`

There is no environment variable for it, and no walking up parent directories.
Both turn "which file did it actually read?" into a question, and that question
is the first thing a support conversation needs answered. If nothing is found,
the error names all three places and suggests `ga4-realtime init`.

Step 3 exists for one concrete reason: Windows Task Scheduler runs with the
working directory at `C:\Windows\System32` and a systemd unit runs at `/`, so a
lookup that only knew about the current directory would make every scheduled
invocation spell out an absolute path.

### Relative paths, one rule

**Every relative path inside the config file resolves against the directory the
config file is in** — never against the directory you ran the command from. So a
config in a project keeps its keys and its database inside that project, and a
config in the platform config directory keeps them beside itself. `--db` is the
exception, and deliberately so: a path typed at a shell resolves against that
shell, because that is what the person typing it meant.

With `[storage] database` unset entirely, the database lands in the platform
*data* directory — `~/.local/share/ga4-realtime/`, `~/Library/Application
Support/ga4-realtime/`, or `%LOCALAPPDATA%\ga4-realtime\`. On Windows that is
`%LOCALAPPDATA%` and not `%APPDATA%` on purpose: roaming profiles and OneDrive
sync `%APPDATA%`, and a SQLite database in WAL mode is three files that are only
consistent with one another at a single instant. The rotating log always lives
beside the database, whichever it is.

### Per-site keys

Everything in this table can be written under `[defaults]`, where every site
inherits it, or inside a `[[sites]]` block, where that site's value wins.

| Key | Default | Flag | What it is |
|---|---|---|---|
| `credentials` | *required* | — | the service account's JSON key |
| `interval` | `300` | `--interval` | seconds between polls |
| `poll_window` | `10` | — | minutes of realtime history each poll reads, 1 to 30 |
| `conversions` | *required* | — | the events that count as conversions |
| `timezone` | `""` | `--timezone` | IANA name; empty means "ask the Admin API" |
| `label` | Admin API display name | — | what the header calls this site |
| `color` | `[ui] color` | — | this site's chart colour |
| `enabled` | `true` | — | `false`: not polled, not in the `Tab` rotation |

Two keys identify a site, so they can only be written inside a `[[sites]]`
block — inheriting them would give two sites one identity:

| Key | What it is |
|---|---|
| `name` | the slug this site is stored and addressed by: lowercase letters, digits, underscore and hyphen, starting with a letter or digit, at most 32 characters. Treat it as immutable — renaming starts a new history, and the old one stays readable under the old name |
| `property_id` | the numeric property ID, **not** the `G-XXXXXXXXXX` measurement ID |

`color` is per-site because the dashboard shows one site at a time: a distinct
chart colour is what tells you at a glance which site you are looking at,
without reading the header. `enabled = false` stops a site being polled and
takes it out of the rotation while leaving everything it already collected
readable by `report` and listed by `sites` — nothing you collected becomes
unreachable because you edited a text file.

### Global keys

The dashboard shows one site at a time, so a per-site refresh interval or chart
width would change the furniture under the reader on every `Tab`.

| Key | Default | Flag | What it is |
|---|---|---|---|
| `[ui] refresh` | `10` | `--refresh` | seconds between redraws; unrelated to `interval` |
| `[ui] window` | `6` | `--window` | hours on the chart's x axis, 1 to 24 |
| `[ui] top_events` | `10` | — | rows the events table shows before it is cropped |
| `[ui] ascii` | `false` | `--ascii` | plain ASCII plots and bars |
| `[ui] color` | `"cyan"` | — | chart colour for sites that name none |
| `[ui] conversion_color` | `"green"` | — | colour of the conversion markers |
| `[storage] database` | platform data directory | `--db` | the SQLite file every site is written to |

All sites share one database file. `site` leads every primary key, so they never
collide, and one file is what makes a cross-site total a single query.

### A flag beats the file, for every site

**A command-line flag overrides `[defaults]` and every per-site value, for every
site.** `--interval 60` polls every site every 60 seconds even where a
`[[sites]]` block says 120; `--timezone Asia/Tokyo` forces every site's day
boundaries into Tokyo, which is how two properties in different zones become
comparable for one run.

The alternative — explicit per-site config beating the flag — was rejected
because `--interval 60` silently doing nothing for the one site you were
investigating is exactly the kind of silent no-op the unknown-key warning below
exists to prevent. `--timezone` in particular is a debugging override rather
than a config replacement: the per-site `timezone` key is the place to set one
for good.

### Secrets, and unknown keys

Any string value in the config may be written as `${VAR}` and read from the
environment, or from a `.env` file sitting beside the config. That is what keeps
a key path — or a property ID, if you would rather — out of a file you might
paste into an issue. An unset or empty variable is an error naming both the
variable and the config key that wanted it; it is never quietly substituted with
an empty string. The real environment wins over `.env`, so
`GA4_CREDENTIALS=… ga4-realtime doctor` is a one-off override that edits
nothing. `.env.example`, written by `init`, is the template.

An unknown key is a **warning**, not an error: the tool names the key, suggests
the nearest valid spelling, and carries on. A typo'd `intervall` that silently
did nothing is the outcome worth preventing; refusing to start over a stray key
would only punish you for a future version's spelling.

Everything else is validated at load time, before a single network call: at
least one enabled site, unique usable names, an all-digits property ID, a
credentials file that exists and can be read, a non-empty conversions list,
numbers inside their bounds, and a timezone `ZoneInfo` can resolve. Each failure
names the file to edit and the key inside it.

## What it records

Each poll issues one Realtime request per site over the last 10 minutes
(`poll_window`) — a window deliberately wider than the 5-minute default
interval, so late-arriving events and skipped cycles are re-read and corrected
rather than lost. It is broken down by `eventName`, `deviceCategory` and
`country`, for `screenPageViews` and `eventCount` — the two additive metrics.

Rows are keyed on `(site, minute, event, device, country)` and **upserted**:
re-polling a minute already seen *corrects* the stored row instead of adding to
it. This is the correctness property the whole design hangs on, so the upsert
overwrites every metric column and never accumulates. Quitting and restarting
continues the same history and does not double any total.

Everything lands in one SQLite file, in three tables:

| Table | What is in it |
|---|---|
| `realtime_minute` | the fan-out above, one row per site, minute, event, device and country |
| `poll_log` | one row per poll: rows fetched, inserted, updated, and the error if it failed |
| `site_meta` | each site's property ID, display name and timezone, as the live view resolved them |

**The database is the interface.** There is no `export` command and no
machine-readable output flag, because there is nothing for one to add: this is
plain SQLite at a path the tool prints, in the three tables above, and

```bash
sqlite3 ga4_realtime.db "
  SELECT event_name, SUM(event_count) FROM realtime_minute
  WHERE site = 'mysite' GROUP BY 1 ORDER BY 2 DESC"
```

needs nothing from this tool at all. Minute keys are fixed-width UTC strings, so
plain string comparison orders and ranges them correctly without date functions.

Pointing the tool at a database written by a version before sites existed is
refused in words, naming the file — rather than failing later with
`no such column: site` a page into a stack trace.

## Two things worth knowing before reading the numbers

**There is no user count, of any kind.** The same visitor appears in
consecutive minute windows, and the Realtime API exposes no identifier to
deduplicate on — so `activeUsers` cannot be summed across minutes. Worse, in the
fan-out one visitor firing `page_view`, `scroll` and `session_start` would show
up in three rows of the *same* minute, so it could not be summed across rows
either. It is a concurrency reading and nothing more. There is no honest daily
unique-user count in realtime data, so the tool does not print one.

A second request once collected that gauge per minute, into a `realtime_users`
table of its own, and the dashboard drew it as a chart. Both are gone: the
reading was worth less than the vertical space it cost, and dropping it halves
the API calls per poll. For a while afterwards the empty table survived in
databases created before the change, because dropping it would have destroyed
collected history to reclaim a few kilobytes; the schema here is a fresh one, so
it is not created at all.

Google enforces this rather than merely documenting it: asking for
`activeUsers` alongside `eventName` is rejected with *"Selected dimensions and
metrics cannot be queried together"*, because one is user-scoped and the other
event-scoped. So the fan-out table has no `active_users` column at all — there
is nothing there to sum by mistake.

**There are no page paths.** The Realtime API has no `pagePath` dimension —
only `unifiedScreenName`, which on web returns the page *title*. On a one-page
site that is close to useless, so the breakdown is by `eventName` instead,
which has the side benefit of putting a conversion event on screen live.

## Notes

- Day boundaries use the **property's** timezone, never the machine's, fetched
  from the Admin API at startup and cached in the database. The per-site
  `timezone` key overrides it permanently; `--timezone` overrides it for one
  run, for every site at once. This is what `tzdata` is a dependency for.
  Two sites in different zones roll over at different moments, and `Tab` can
  move between a site at 23:40 and one already at 04:40 the next day. That is
  correct, and the header's timezone and clock are what make it legible.
- The cumulative chart marks every minute in which any configured conversion
  fired with a `*` along the baseline, so the conversion is legible against the
  traffic that produced it. The markers sit on the baseline rather than on the
  curve because a terminal cell is coarse enough that a star placed at the
  running total lands a row off the line as often as on it. The y axis is whole
  numbers — page views are counted, not measured, and an axis labelled `5.50`
  claims half a page view happened. The line runs out to the current minute:
  while the poller is live, a minute with no rows really did have no page views.
  If polling stalls, that flat run means "not collected" instead — which is what
  the header's reddening `last poll … ago` is there to say.
- **The chart's x axis is a trailing window ending now — 6 hours by default,
  `--window HOURS` (1–24) or `[ui] window` to change it — not a fit to the
  recorded data.** Fitting the axis to the data stretched ten minutes of a fresh
  run across the whole panel and rescaled the chart on every poll; a fixed
  window slides forward with the clock instead and stays still. Two things
  follow. The y values remain cumulative since local midnight, so later in the
  day the curve enters the window at a height rather than at zero — the level it
  enters at is carried from the last point before the window, not interpolated.
  And before roughly 06:00 the left of the axis is empty, because the window
  reaches back past midnight while the series is day-scoped; that is preferred
  over clamping it to midnight, which would put the stretched-out look back for
  the first hours of every day. Everything else — the footer totals, the events
  table, `report` — stays day-scoped and ignores the window.
- `report --site all`, and the piped form, print one section per site scoped to
  **that site's** local day, and then — when the run covers more than one site —
  a combined total labelled *"sum of each site's local day"*, with a warning
  line naming the zones involved when they differ. The arithmetic is stated
  rather than implied: totalling every site over one shared window was rejected
  because each site's contribution would then disagree with its own single-site
  report, which is a worse kind of wrong than a labelled sum.
- Startup primes every site concurrently before the dashboard opens, so startup
  costs one round-trip rather than N, and every credential, permission and
  timezone failure is reported plainly while stdout is still an ordinary
  terminal. A site that fails starts with a `✗` in the status strip and the run
  continues — one bad key must never hide two working sites. Only if *every*
  site fails does the tool exit without opening the display.
- An API error mid-run backs off exponentially with jitter and is logged; the
  dashboard keeps rendering, and the site's marker says what happened.
- Logs go to a rotating file beside the database, never to stdout — stdout
  belongs to the live view, and a stray line tears the display. `--verbose` adds
  a log panel to the layout, carrying every site's lines with its name.
- `--ascii` drops to plain ASCII everywhere, and is enabled automatically if the
  console encoding cannot represent block characters. `NO_COLOR` is respected.
- The rendered frame never exceeds the terminal: height is allocated from a
  budget, and when it runs short the order of sacrifice is fixed — the log panel
  first, then table rows, then the chart entirely. The header and footer are
  never sacrificed, because a frame that cannot say which site it is about or
  how stale the numbers are is not worth the rows it saved.
- The tool only ever reports. Thresholds and alerting wait until there is enough
  collected history to calibrate them against real numbers.

## What it does not do

**Collection stops when the dashboard does.** There is no service, no daemon and
no scheduled mode: the process that draws is the process that polls, so closing
the terminal ends collection, and with several sites configured that gap
multiplies rather than closes. This is an accepted limitation of this version,
not an oversight — a headless collector for Task Scheduler or systemd is the
obvious next thing, and the collection layer is deliberately free of any
dependency on the display so it can be reused whole rather than reimplemented.

There is also no web UI, no HTTP server and no hosted component; no alerting; no
page-path dimension, and no user metric of any kind. The last two are properties
of the Realtime API and of arithmetic respectively, and are explained above.
